# 阅读器

Stage 7 落地的阅读器。语义事实来源是
`specs/contracts/fixtures/reader/{paging,manifest,prefetch,throttle}.json` ——
Rust 核心与 Swift 核心各自加载同一批文件，两端不许各写一套规则。
实现位置与验收状态见 [Stage 7 验收清单](stage7-checklist.md)。

## 模式与方向

三个**模式**决定「一页还是两页一屏」，三个**方向**决定「屏幕上怎么排、手势往哪走」；
两者正交，配对规则与方向无关。

| 模式 | 一屏内容 | 轴 |
| --- | --- | --- |
| 单页 | 1 页 | 由方向决定（横排 / 纵排） |
| 双页 | 2 页配对，封面页可单独，末尾落单 | 同上 |
| 条漫 | 1 页一行的连续长列 | 恒为纵向，永不配对 |

| 方向 | 屏内先后 | 前进手势 | 点按前进 |
| --- | --- | --- | --- |
| LTR | 阅读序 | 向左划 | 右半屏 |
| RTL | 反转（阅读首页在右） | 向右划 | 左半屏 |
| Vertical | 阅读序（上→下） | 向上划 | 下半屏 |

关键点：**RTL 从不改变「下一页是哪一页」**。它只改屏内先后与手势方向；
读序永远是页码增序（`paging.json` 有专门用例与一条「前进必单调」性质测试钉住）。

宽或高未知的页不参与配对 —— 无法证明它是半页，就不该把它塞进跨页里
（它自成单页，配对从下一页继续）。EPUB / PDF 不进图像阅读器：走文件查看器与
progression 接口，这是 Stage 6 规则 R8 在清单层的落实。

## 页面加载

```text
Reader (UI)
  → Page Loader        页号 → 本地文件
  → Offline Download   downloads/{serverId}/{bookId}/0001.png   ← Stage 9，最高优先
  → Page Cache         cache_entries 记账 → cache/pages/<key>.<ext>
  → Page Manifest      规范页号（1 起，来自镜像的清单）
  → 本地文件            解码 + 渲染（平台侧；核心不解码）
```

Stage 9 之后加载优先级是 **Offline Download → Page Cache → Network**，
一个插入点：`App::reader_page_path`（同步、不碰网络）先问
`downloads::recover::usable_page`——行说 `complete` **且** 文件在 **且**
容器首尾按行里记的字节数走得通；任一不符就**顺手写下愈合**（行回 `pending`、
坏文件删掉），然后落到 Page Cache。`reader_page` 第一步就调 `reader_page_path`，
所以显示路径与取页路径共用同一条优先级，不必各写一遍。

下载页**不**写 `cache_entries`、**不** `touch`：它不是缓存状态。预取的暖集合
（`prefetch_warm_set`）里包含已下载的页，否则泵会把用户已经付过钱的每一页重新排一遍、
再往缓存层写第二份。边下边读不需要任何协调：`land_page` 的原子 rename 就是协议——
读者要的页要么已经是完整文件，要么还不存在，它不会等，也不会看到半页。

两条分层规则：

1. **UI 里没有网络请求**。翻页只要一个文件路径；取清单、取页字节都在核心侧，
   通过注入的 `PageSource` / `PageFetcher` 到达，所以「UI 顺手发个请求」在结构上不可能。
2. **核心不自己发明线上格式**。进度写入的 body 复用 Stage 6 的
   `outbox::request_for` / `requestFor`，两端共用一份冲突规则。

清单先镜像后使用：`book_pages` 存归一化后的页表，开过的书第二次打开是纯本地操作
（回环验收用**服务器页读取日志零增长**证明这一点）。

## 缓存分层

```text
读一页                        预取一页
  │                             │
  ▼                             ▼
Memory Cache（字节预算 LRU）──命中──→ 直接落 pages/ 并返回路径
  │ miss                          │
  ▼                               ▼
cache_entries + 文件（完整性校验）   落 prefetch/ + 字节驻留内存
  │ prefetch 行 → 提升为 page 行（rename，不重下不复制）
  ▼
本地文件路径 → 平台解码
```

三层目录 `Cache/{thumbnails,pages,prefetch}/`。分层的唯一理由是**淘汰次序**：
读者真正看过的字节比猜来的值钱，`prefetch` 永远先被牺牲，与新旧无关。

离线下载**不在这三层里**：它住在 `cache/` 的兄弟目录 `downloads/`，也不进 LRU 账本。
所以"LRU 永不删下载"不是淘汰代码里的一条 `if`，而是 `PageCache` 根本说不出那个路径
（它只能通过 rooted 在 `cache/` 的 `DiskCache` 拼路径）——见
[offline-storage.md](offline-storage.md)。账本里 `kind='download'` 那道围栏还在，
但它是围栏，不是机制。

## 页缓存

| 约定 | 规则 |
| --- | --- |
| 命中 | 记账行在 **且** 文件在 **且** 完整性通过（写盘 `.part` + rename；命中前再做 head+tail 快检，见下）|
| 键 | `safe_key("{serverId}-{bookId}-p{页号}")`，与封面同一 sanitizer、同一 LRU 池 |
| 扩展名 | 跟着**响应** Content-Type（服务器可能转码），本地路径只从 SQLite 读，不许自己拼 |
| 记账大小 | 落盘后的真实字节数，不是清单声明的 `sizeBytes` |
| 淘汰 | 先 `prefetch` 后 `page`，各自按 `last_access`（同刻按 key 定序）；`kind='download'` **永不**淘汰；**触发淘汰的那一条本身不可淘汰**（同一毫秒的平局按 key 排序会把它选走，实测 4K 书因此每页下载两次）|
| 预算 | `DEFAULT_BUDGET_BYTES = 512 MiB`，UI 可经设备档案下发覆盖；热路径判预算用免 stat 的 `SUM`，逐文件对账只在 open 时做一次 |
| 完整性 | 写入时全量走容器（PNG 逐 chunk CRC、JPEG 段长与 EOI、GIF 结束符、WebP RIFF 长度），命中时只读头尾；截断页 / HTML 错误页 → 丢弃 + 重取，连拒两次即停止重试 |
| 认不出的格式 | AVIF / HEIC / BMP / JPEG XL 判为「看不懂但保留」——本模块不能走它的容器，不等于它坏了 |
| 账实对账 | `reconcile`：幽灵行、孤儿文件、`.part` 残片、字节数不符、kind 与所在目录不符。分歧时**以磁盘为准**，磁盘才是证人 |

## 相邻页预取

窗口以**跨页**为单位（双页模式下「前一页」会漏掉半屏）：当前跨页 → 后向 F 跨 → 前向 B 跨，
次序确定且被契约逐例断言；缓存页仍占名额；`cap` 从尾部裁。
中心跨页移动时旧窗口作废，但**已在途的下载不砍**：半截文件比白下一张更糟。

**F/B/cap/并发数/内存层大小由 `window.json` 每次开书算出来**，不是常量：
内存 → 页成本 → 装得下几页（其中 1/4 给前瞻）→ 模式（条漫前看翻倍、后看最多 1）→
字节上限（≤ 2×内存层，且 ≤ 磁盘池的一半）→ 网络（离线=0，弱网=3 且单并发，蜂窝减半）→
是否稳定（快翻中只取当前跨）。方向不参与：窗口按阅读序跨页计，ltr/rtl 必须同解，
契约用成对用例钉住这一点。`forward=2 / back=1 / cap=12` 降级为「UI 没交设备档案时」的兜底。

## 阅读进度

```text
Reader
  → reader_position   显示状态：页 + 当时的模式与方向（永不上云）
  → read_progress     与 Komga 同步的那一份
  → pending_mutations 同族合并后的待上传行（一本书最多一行）
  → 节流上传 Komga     sync::upload::upload_outbox
```

一句话：**节流只管网络，不管持久性**。每次真实翻页都在同一个调用里落
位置 + 进度 + 队列行，所以 `kill -9` 落在两次翻页之间也不丢用户动作；
重开时那行债务在第一次机会就送出去。

| 规则 | 内容 |
| --- | --- |
| T1 | 真实翻页立即写库（本地永远领先网络） |
| T3 | 只有**节拍**看间隔（5 s）；翻页本身从不发包 |
| T4 | 标已读 / 标未读 / 退出 / 后台 = 立刻冲，不等间隔 |
| T5 | 规范页 1 起，`page 0` 钳到 1，永不外发（Stage 6 R7） |
| T6 | 翻到末页 = `completed=true` 的进度写，**不是** MARK_READ（两者 body 可区分） |
| T7 | 回翻是合法变更：新动作优先（Stage 6 冲突规则，不统一 max(page)） |
| — | MARK_READ 只发 `{"completed":true}`，不顺手改写服务器上的页码；本地镜像同理（COALESCE 保留原页） |
| T9 | EPUB / PDF 不进这条流 |

30 页突发 → 30 次本地写 → 1 行队列 → **1 个**请求，携带最后一页。

## 阅读设置

阅读方向 · 页间距（0..=64 逻辑像素）· 背景（黑/灰/白）· 屏幕常亮 · 基础亮度 · 阅读位置恢复。
除亮度外都存在 `app_state!reader_settings`（一份 JSON 文档，加旋钮不需要迁移）；
亮度是设备状态，关书即交还系统。

模式与方向的优先级是**两级，且只有两级**：
**本系列的覆盖（`app_state!reader_override:[serverId,seriesId]`）> 全局默认**。
书上一次是怎么读的**不再参与决策** —— `reader_position.mode/direction` 两列仍然
照写（见 `store::position`），但打开时不再读它来定模式。

同系列的所有册因此不可能互相矛盾，而"我在第 3 卷按了一下双页"也不会再把第 9 卷
变成跨页：阅读器里的切换写当前系列的覆盖，并在界面上说清"已把此系列设为…"，
所以"跟随全局"仍然是一句可核实的陈述。

> 本节此前写的"上一本书记住的 > 服务器 series 元数据推荐 > 全局默认"三级顺序与代码
> 不符：服务器推荐那一档在真实打开路径上从未被传入（`resolve_direction` 的第二个
> 参数恒为 `None`），只有单测覆盖它。已按第一里程碑的产品规则改为两级。

## 链路状态怎么来的

核心不探测网络（也拿不到权限），由 UI 报告，而 UI 也只从**请求的结果**推断：

| 观察 | 报告给核心 | 核心的反应 |
| --- | --- | --- |
| 连续两次「试图联系服务器」失败 | `offline` | 队列长度 0：一个请求都不再发 |
| 慢响应累计 3 次 | `weak` | 名额 3、单并发 |
| 用户报的按量链路 | `cellular` | 名额减半、并发 ≤2 |
| 一次**真的取到了东西**（`landed > 0`）| `wifi` | 恢复正常窗口 |

「什么都没得取」不算证据：预取在没东西可取时返回 0，链路死了也返回 0 —— 把它当成
链路健康会让离线永远推不出来（真机上就是这么漏的，见验收清单缺陷 8）。

## 性能（Stage 8 实测）

520 页整本读完 520 次页请求、RSS 峰值 13 MB、池 33.8 MB ≤ 64 MB 预算，
后 1/4 每跨均耗 6367us vs 前 1/4 6620us（**长会话不增长**）；
条漫 300 次推进暖页 p50 153us / p95 182us / p99 200us；
真 4K 页（24,887,323 字节/页）下窗口自动收到 cap=1，同一本书同一池子
占位窗口 15 次请求 vs 计划窗口 7 次；内存层从 256 MiB 收到 32 MiB，
进程 RSS 从 229 MB 降到 154 MB（**是上限不是泄漏**）；
断网 21 页全走磁盘、0 请求；后台恢复第二个进程 0 请求（服务端日志独立确认）；
真实 Komga 上整本读完一本 292 页的真书：292 次页请求 = 292 个不同页、清单 1 次。
完整 70 项见 [Stage 8 验收清单](stage8-checklist.md)。

仍未测：真机（硬件 GPU 手机）上的帧率与低内存 OOM 边界——APK 能构建，
`e2e_stage8_device.sh` 已在 API 35 模拟器上驱动真实阅读器取到 PSS 与每页墙钟（20 项全绿），
但绝对毫秒与 OOM 余量只算指示，需 `--device <序列号>` 复测。
另外真实库里最大的单本就是 292 页，「500+ 页」那一档仍只有合成书证明。
